Van executable tot app in je broekzak

Hoe werd een programma een moderne app?

Een smartphone-app lijkt iets totaal anders dan een oud programma op een pc. Onder de motorkap zijn dezelfde basisideeën nog altijd aanwezig: code draait in processen, processen praten via netwerken, services verwerken requests en data wordt ergens opgeslagen.

Les 1

Programma, proces en service

Alles begint met code. Maar code op een schijf doet niets. Pas wanneer het besturingssysteem die code laadt en uitvoert, ontstaat een proces.

Een programma is code op opslag

Een klassiek programma bestaat uit uitvoerbare code en vaak extra bestanden. Op Windows kan dat bijvoorbeeld een .exe zijn. Op Linux hoeft een uitvoerbaar bestand geen extensie te hebben.

Van bestand naar actief proces
opslag                     geheugen / CPU

programma.exe  --start-->  proces
                              |
                              +-- instructies uitvoeren
                              +-- geheugen gebruiken
                              +-- bestanden openen
                              +-- vensters tonen
Programma ≠ proces Het programma is de opgeslagen code. Een proces is een draaiende instantie van die code. Je kunt hetzelfde programma meerdere keren starten en dus meerdere processen hebben.

De eerste toepassingen deden bijna alles lokaal

Klassiek lokaal programma
+------------------------+
| tekstverwerker         |
|                        |
| gebruikersinterface    |
| logica                 |
| bestanden lezen/schrijven
+-----------+------------+
            |
            v
      document.doc

De applicatie, de logica en de gegevens zaten dicht bij elkaar op dezelfde computer. Een netwerk was niet noodzakelijk.

Dan komt het achtergrondprogramma

Sommige programma's moeten niet alleen draaien wanneer iemand op een icoon klikt. Ze moeten beschikbaar blijven. Op Windows noemen we zulke achtergrondprogramma's vaak services; op Unix/Linux kom je ook het woord daemon tegen.

ServiceTaakWacht bijvoorbeeld op
sshdExterne terminalverbindingenEen SSH-verbinding
webserverWebpagina's of API-antwoorden leverenHTTP-requests
database-serverGegevens opslaan en opvragenDatabasequeries
printservicePrintopdrachten beherenNieuwe printjobs
Een service is nog altijd gewoon software Het bijzondere is vooral dat ze langdurig op de achtergrond draait en een functie aanbiedt aan andere processen of computers.
1A

Praktijk: zoek draaiende software

Maak het verschil tussen programma, proces en service zichtbaar.

  1. Open Windows Taakbeheer.
  2. Zoek een programma dat je zelf hebt geopend, bijvoorbeeld een browser.
  3. Bekijk hoeveel processen erbij horen.
  4. Open het onderdeel Services en zoek drie services die draaien zonder zichtbaar venster.
  5. Leg in één zin uit waarom een service geen apart zichtbaar venster nodig heeft.

Van één computer naar client en server

Zodra meerdere computers dezelfde gegevens of functies nodig hebben, wordt het interessant om een deel centraal te laten draaien.

De client vraagt, de server antwoordt

Client en server beschrijven een rol. Een client start meestal een aanvraag. Een server luistert en behandelt aanvragen. Eén computer kan tegelijk client én server zijn voor verschillende toepassingen.

2A

Praktijk: herken de rollen

Bepaal per situatie wat client en server is.

  1. Je browser opent https://example.com.
  2. Een mailprogramma haalt berichten op van een mailserver.
  3. Een app vraagt leerlinggegevens op via een school-API.
  4. Een pc stuurt een printjob naar een centrale printserver.
Controle
In alle vier situaties is het programma dat de aanvraag start de client. De webserver, mailserver, API-service en printserver leveren elk een service aan die client.

Wat is een API?

Een API is een afgesproken interface waarmee software andere software kan aanspreken. Bij webapps bedoelen we vaak een HTTP-API.

Voorbeeld HTTP-request
GET /api/students/123 HTTP/1.1
Host: school.example
Voorbeeld JSON-response
{
  "id": 123,
  "name": "Jan",
  "class": "5ICW"
}
JSON is geen JavaScript-object JSON is tekst in een afgesproken formaat. JSON.parse(tekst) maakt er in JavaScript gegevens van; JSON.stringify(object) maakt JSON-tekst.

Veelgebruikte HTTP-methoden

MethodeTypisch doelVoorbeeld
GETGegevens lezenGET /students/123
POSTNieuwe actie/resource starten of makenPOST /students
PUTResource volledig vervangenPUT /students/123
PATCHResource gedeeltelijk aanpassenPATCH /students/123
DELETEResource verwijderenDELETE /students/123

Les 4

“De server” wordt een heel systeem

Voor een kleine toepassing kan één backendprogramma perfect voldoende zijn. Grotere systemen worden soms opgesplitst in meerdere services met elk een eigen verantwoordelijkheid.

Eerst: de monolith

Eén applicatie
+--------------------------------+
| SCHOOLAPP                      |
|--------------------------------|
| gebruikers                     |
| leerlingen                     |
| punten                         |
| berichten                      |
| betalingen                     |
+---------------+----------------+
                |
                v
             database

Een monolith is niet “slecht”. Voor kleine en middelgrote toepassingen is één duidelijke applicatie vaak eenvoudiger te ontwikkelen, testen en beheren.

Opsplitsen in services

Meerdere services
                 +-- user service
                 |
app ---- API ----+-- student service
                 |
                 +-- notification service
                 |
                 +-- payment service

Wanneer services zeer klein en onafhankelijk worden opgezet, spreken we vaak over microservices. Dat kan schaalbaarheid en teamautonomie helpen, maar brengt ook extra netwerkverkeer, monitoring, deployment en foutafhandeling mee.

Meer services is niet automatisch moderner of beter Architectuur is een keuze op basis van schaal, team, betrouwbaarheid en complexiteit. KISS blijft een geldige ontwerpregel.

En dan: cloud

“Cloud” betekent niet dat de server verdwenen is. De software draait nog altijd op echte computers, maar infrastructuur wordt als dienst aangeboden en kan makkelijker worden geautomatiseerd of opgeschaald.

Les 7

Onze combinatie: Vite + PWA + Capacitor

Deze combinatie vertrekt bewust vanuit webtechnologie. Eerst maken we een gewone webapp. Daarna voegen we installatiemogelijkheden en native verpakking toe.

Elke laag heeft één taak

LaagRol
ViteOntwikkel- en buildtool. vite build maakt een productie-bundle van de webapp.
FrameworkOptioneel: React, Vue, Svelte... of gewoon vanilla JavaScript. Dit staat los van Vite/PWA/Capacitor.
PWAManifest + service worker + caching zodat de webapp installeerbaar/offlinevriendelijker kan worden.
CapacitorPlaatst dezelfde webapp in een native project/container voor iOS en Android.
Capacitor pluginsGeven JavaScript toegang tot native functies zoals camera, filesystem, preferences en push.
Eén webcodebase, meerdere doelen

                       Vite
                        |
                 productie-build
                        |
          +-------------+-------------+
          |                           |
          v                           v
       WEB / PWA                  CAPACITOR
                                      |
                              +-------+-------+
                              |               |
                              v               v
                           Android           iOS
                              |               |
                       native plugins   native plugins

Minimale werkwijze

Terminal
npm create vite@latest
cd mijn-app
npm install
npm run dev

Daarna voeg je PWA-functionaliteit en Capacitor toe wanneer de webapp zelf werkt.

PWA en Capacitor toevoegen
npm install -D vite-plugin-pwa
npm install @capacitor/core @capacitor/cli
npx cap init

npm run build
npx cap add android
npx cap sync
Belangrijk: Vite is geen app-framework Vite helpt je project ontwikkelen en bouwen. React, Vue of Svelte bepalen eventueel hoe je UI-code structureert. Capacitor verpakt het uiteindelijke webresultaat.

Sterke punten

  • Dezelfde HTML/CSS/JavaScript-basis kan web, PWA, Android en iOS bedienen.
  • Bestaande webkennis blijft bruikbaar.
  • Een interne tool kan eerst gewoon als PWA worden uitgerold.
  • Native functies kunnen later gericht met Capacitor-plugins worden toegevoegd.
  • De backend blijft dezelfde API gebruiken ongeacht de client.

Beperkingen

  • De UI blijft in hoofdzaak webtechnologie in een WebView en voelt niet automatisch identiek aan een volledig native UI.
  • Voor zeer zware animaties, games of complexe grafische interfaces kan een andere aanpak beter passen.
  • Voor diepe achtergrondintegratie of zeldzame hardwarefuncties kan eigen native code nodig zijn.
  • Voor een iOS-build blijft Apple-tooling nodig; praktisch betekent dit Xcode op macOS.
  • Een Capacitor-app in een store blijft onder de distributie- en reviewregels van die store vallen.

Waarom dit voor onze kleine schoolapps vaak logisch is

KISS→webapp→PWA→pas indien nodig Capacitor

Voor een eenvoudige schooltool met formulieren, lijsten, een backend-API en beperkte hardware-integratie hoeft een native app niet de eerste stap te zijn.
